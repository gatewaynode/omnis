# Plan: P0 (vector reads views) and P1 (dev socket in vector), then the presentation architecture

## Context
The owner chose to start with parity items P0 and P1 (`tasks/TODO.md`, "Vector adoption"), then the architecture of the presentation layer.
- **P0.** `omnis-vector` reads `World` fields directly: 37 reads in 15 files. TODO's count of 30 in 13 missed `collide.rs` and `shell/hud.rs`, where the world is aliased as `w`. ARCH A17 and §4.9 say a client reads only views, and `omnis-app` is held to that by the compiler through its private `SimWorld` (M8 8d/8e). Vector has no such guard.
- **P1.** Window-mode MCP (`screenshot`, `screen_text`, and driving the game) talks to the dev socket, which only `omnis-app` hosts. Moving it to vector lets agents capture and drive the client the visual steps will change.
- **Afterwards:** `presentation-ARCHITECTURE.md` still describes the Phase A experiment ("no dev socket", "Omnis Alt", a fixed party). It needs rewriting as the architecture of the presentation layer.

## Findings that shape the design
- **Two gaps in the views:**
  - **Door state across a map.** `geometry.rs:53`, `collide.rs:32` and `shell/actions.rs:30` read `world.maps[..].door_open` for any edge. `viewport` covers only the visible cone, `Known` records that a door exists but not whether it is open, and `map_text` is text.
  - **Whether a member can fight.** `shell/fight.rs:13` calls the internal `combat::state::can_fight`. `MemberView` has `down` and `dead` but no flag for incapacitated.
- **Everything else is covered:**
  - mode → `here().mode` (`ModeKind`)
  - position → `here().position` (a `Place`, converted back the way `omnis-app/src/defs.rs:67` does)
  - town → `here().service`
  - party → `party_view`
  - the first live stack → `combat_view`
  - the clock → `here().age`
  - the minimap → `automap(world, map)`
- **The socket's op handling is already shared.** `omnis_sim::ops::{Op, Reply, OpError, dispatch, rules_set, save_text, load_text, check_reload, client_path}` are in the crate vector already uses. What is app-specific (541 lines in `omnis-app/src/socket.rs`) is the framing, the host ops, Screenshot and ScreenText. `serde_json` is already pinned in the workspace (`=1.0.150`), so no new crate.
- **The binder must see socket commands.** `dispatch` calls `apply` directly, so `sim.command`, `sim.script`, `party.create` and `time.reconcile` would skip the binder's log (the session replay), `Session::note` (HUD lines, roll log, reshape) and `Session::follow` (snapping the pose).

  - `can_fight` is false for a member at 0 hp and for one with an incapacitating condition, and true otherwise.
- **Docs:** `docs/api.md` gets entries for both. `crates/omnis-mcp/tests/api_doc.rs` checks the doc covers them.
- **Constraints:** no floats, no HashMap, `lint-sim.sh` passes, both replays unchanged, `SAVE_SCHEMA` stays 7.

## P0b. Vector reads views, and the compiler holds it there
- **New Bevy-free `crates/omnis-vector/src/sim.rs`**, modelled on `omnis-app/src/sim.rs:115-261`:
  - `SimWorld(World)` with a private field, `Clone`, and methods that mirror the API:
    - `apply`
    - `trial` (a clone plus `apply`, replacing `trial.rs`'s `world.clone()`)
    - `dispatch`
    - `views`, `automap`, `door_open`, `step_lands`
    - `save_text`, `status`, `check_reload`, `replace`
    - `fixture()`/`fixture_mut()`, only under `cfg(test)` or a new `test-fixtures` feature
  - `Views {here, position: Position, party, combat}`, built by `Views::of`. `position` is `here.position` converted through `data.registry.maps`, the same way `defs::position` does it.
- **`Binder::apply`/`advance`** take `&mut SimWorld`. They read the mode and position from `here`, not from `world.mode` and `world.position`.
- **`collide`, `geometry` and `actions`** read doors through `door_open`.
- **`Session.world: SimWorld`**, private. Its `views` are refreshed after every accepted command and every world replacement, all through one `Session` path.
- **Shell readers move to `session.views`:**
  - `hud`, `panel`, `movement`, `render`, `minimap`, `town`, `fight`, `cinema`
  - `combat_menu` and `rolllog`, which read party names and ids
  - The internal imports of `Mode`, `can_fight` and `ops::party_view` go: `ModeKind` and `party_view` come from `omnis_sim::api`.
- **Guard:** `scripts/verify.sh` and `.github/workflows/ci.yml` get `cargo clippy -p omnis-vector --no-default-features --lib -- -D warnings`, as `omnis-app` has. The library then can't call `fixture()`, so a direct read fails to compile.
- **Tests:**
  - Integration tests build and inspect fixtures through `fixture()`/`fixture_mut()`. There is a dev-dependency on itself with `test-fixtures`, as in `omnis-app/Cargo.toml:38`.
  - A new test: after a scripted walk, a door and a fight, `session.views == Views::of(fixture)`, so the cache never goes stale.
- **No behaviour change.** The agreement test, all 87 vector tests and both replays stay green, and the pose and HUD captures look the same as before.

## P1. The dev socket in vector
- **Feature and dependency:** `devtools = ["dep:serde_json"]`, on by default; `serde_json = { workspace = true, optional = true }`. Release builds use `--no-default-features`, as `omnis-app` does.
- **`src/shell/socket.rs` (`DevSocketPlugin`)** is a port of `omnis-app/src/socket.rs`:
  - The same `.omnis/dev.addr` file, `127.0.0.1:0` by default, loopback only, one client at a time, and a `MAX_LINE` of 1 MiB.
  - `parse_request`/`encode`, with their unit tests, and the polled non-blocking listener in `Update`.
  - Flags: `--dev-socket <ip:port>` and `--no-dev-socket`. There is no socket in `--screenshot` capture mode.
  - These parts are copied from `omnis-app`, and the copy there goes away at P9. A shared crate isn't worth it for a duplicate that has an end date.
- **Bevy-free host, `src/host.rs`**, modelled on `omnis_cli::Headless::handle` (`omnis-cli/src/headless.rs:57-89`). It takes `&mut Session` and an `Op`, and returns `Result<Reply, OpError>`:
  - **Read ops** go to `SimWorld::dispatch` unchanged.
  - **Mutating ops** (`sim.command`, `sim.script`, `party.create`, `time.reconcile`) also go to `dispatch`, so the rules and replies stay the engine's. Then the accepted commands are recorded in the binder's log:
    - The single command on `Ok`.
    - The first `applied` of a script.
    - After that, `Session::note` and `follow` run.
    - Socket rejections are not counted as binder refusals, since those count client bugs.
    - Nothing in `dispatch` is reimplemented.
  - `save.write`, `rules.set`: the same as `Headless`.
  - `save.read`, `pack.reload` replace the world through `SimWorld::replace`:
    - The pose, names and reshape reset.
    - The binder log is marked as broken at the load, so Save log refuses with a reason. A replay starts from `World::new`, so a log after a load can't replay.
- **Screenshot (both targets):**
  - Vector has no separate canvas, so `canvas` and `window` both capture what the window shows.
  - The active camera (the 3D view or the fight's `Camera2d`, whichever has `IsDefaultUiCamera`) is retargeted to an image of the window's physical size for a few settle frames. Then `Screenshot::image` is saved as an RGB PNG at the `client_path`-checked path, and the target is restored.
  - This captures exactly what is drawn: lines, bloom and UI. It also works when the window is hidden, where a primary-window screenshot comes back black.
  - The cost is a few frames during which the visible window doesn't update. That's acceptable for a dev tool, and `api.md` will say so.
  - Without a renderer it fails with "no window to capture".
- **ScreenText:**
  - Walk the UI tree, as `omnis-app/src/ui_text.rs` does. List every `Text` and `Button` under each root node: the rectangle from `ComputedNode` when layout has run, `[button]`, the text, and `(hidden)`.
  - This covers the HUD, the panel and the fight screen, and any future screen gets it with no per-screen code.
  - The reply is `Reply::Text`.
- **Docs and strings:**
  - `omnis-mcp/src/backend.rs:108-112`: the hint names `just run` instead of `cargo run -p omnis-app`.
  - The ARCH §9 status note says vector hosts the socket and `omnis-app` still does when run.
  - `docs/api.md` §3, §5 and §11: vector is the host, the two screenshot targets are the same in vector, and `MAX_LINE`'s citation.
  - `presentation-ARCHITECTURE.md` §12: the dev socket under `devtools`.
  - Both clients write the same address file, so the last one started wins. Docs say so.
- **Tests:**
  - A `socket` module in vector's `integration` binary, ported from `omnis-app/tests/socket.rs`:
    - The `MinimalPlugins` harness and a real `TcpStream` peer.
    - Status, a step whose events reach the HUD and pose and land in the binder log.
    - `map.text`; refusals (not JSON, an unknown op, `../x.ron`, no renderer).
    - Save and load, with the log marked; `party.get`.
    - `screen.text` listing the HUD and an open panel's buttons.
    - A second client is turned away; a flood over `MAX_LINE`; reconnecting.
  - Unit tests for `parse_request`/`encode` and for `host.rs`. The script's log records exactly the first `applied` commands, and a replay of the binder's log after socket commands reproduces the world's fingerprint.
- **Out of scope for P1:** a devtools switch in vector's settings. The world starts with `Settings::default()`, so `time.reconcile` answers `DevOnly` until P2's new-game screen brings settings.
