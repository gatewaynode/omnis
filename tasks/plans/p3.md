# Plan: parity P3, character creation

## Context
P3 is the next parity step after P2 (presentation-ARCHITECTURE v0.4 §4.4, §6.3, §6.7). A new game from
the title still takes `party::fixed()`. P3 adds the old client's party creation, rebuilt on the screen kit.
Under VA9 the rules shown on screen come from the engine: today `omnis-app` reads `point_budget`,
`score_min/max`, `point_cost` and class skill lists straight from `Data`, which §4.4 calls a defect.

Owner answers (2026-10-10):
- The creation view goes in Tier 1, plus a Tier 2 op and an MCP tool.
- Start again re-creates the same party.
- Scores are edited by slider plus arrows.

**Findings that shape the plan:**
- **The engine already checks a draft fully.** `rules::create` (`omnis-rules/src/character.rs:192`) checks
  in this order, before any change:
  1. party full (`omnis-sim/src/party.rs:120`)
  2. name: 1..=32 bytes after trim
  3. race, class and background ids
  4. score range
  5. points spent ≤ budget
  6. exact skill count, skills on the class list, and not a skill already granted
  
  The client's Add can therefore take its reason from a trial (`trial::refusal`) rather than repeat the rules.
- **No creation mode in the world.** `World::new` starts in Explore with an empty party, and Party
  commands are accepted in Explore or Town. "Creating" is client state, as in `omnis-app`
  (`PlayState::CreateParty`).
- **An empty party counts as fallen.** `Views::fallen()` is `!any(can_fight)`, so with zero members it is
  true. CreateParty must be decided before Defeat in `nav::base`.
- **Some point-buy defaults are written twice.** `stats.rs:47-49`, `character.rs:214` and `party.rs:15-18`
  each carry their own fallback. The view must read them from the same place as the engine's check.
- **Grants trip the old client.** Acolyte grants Insight, which is on the rogue's list. The old client
  allowed the pick, and the engine refused it with "skills: Insight is already proficient".
- **Wire names already taken:**
  - `budget` (the action `Budget`, `view.rs:151`)
  - `skills` (`MemberView.skills`, `Vec<(Skill, i64)>`)
  
  The new fields avoid both.
- **The slider is free.** `bevy_ui_widgets::Slider` is in `DefaultPlugins` (`UiWidgetsPlugins`). It raises
  `ValueChange<f32> { source, value }`, an EntityEvent with public fields that tests can trigger. Its thumb
  is positioned by the app (`SliderRange::thumb_position`). Floats are allowed in this client crate; they are
  rounded to an integer at the router.
- **Panels:** every screen today has a single panel, so laying panels out side by side breaks nothing.

## P3a. The engine: the creation view (additive, protocol 2)
- **New `omnis-sim/src/creation_view.rs`:** `creation_view(data: &Data) -> CreationView`. It is built
  from the functions the check uses, so it cannot drift from the check.
  - `slots`: from `party::slots`
  - `name_max`: `NAME_MAX_BYTES`
  - `score_min`, `score_max`
  - `points`: the budget
  - `costs: Vec<u32>`: the cost of each score from min to max, through `stats::point_cost`
  - `races: Vec<RaceOption { id, bonuses: [i8; 6], grants: Vec<Skill> }>`
  - `classes: Vec<ClassOption { id, choose: u8, from: Vec<Skill> }>`
  - `backgrounds: Vec<BackgroundOption { id, grants: Vec<Skill> }>`
  - `alignments: Vec<Alignment>`
  - Every list is in the registry's order, which is the order `omnis-app` uses.
- **Single defaults:** new `pub fn point_budget(data)` and `score_range(data)` in omnis-rules
  (`stats.rs`). `create`, `point_cost` and the view all call them, so each default (27, 8, 15) is written
  once.
- **API surface:**
  - Re-exported from `omnis_sim::api`.
  - `Op::CreationGet` with wire name `creation.get`, and `Reply::Creation`.
  - MCP tool `creation_get`, bringing the count to 25 ops and 25 tools. The `party_create` tool's
    description points to it instead of `rules_list`.
  - The MCP schema text "8..=15, 27 points" (`omnis-mcp/src/schema.rs:67`) points to `creation_get`.
- **Docs:** `docs/api.md`:
  - a §7 table row and a §7.x field table for `CreationView`
  - the op in §5/§6
  - "25 ops."
  - §14: the catalogue part of the gap is narrowed
- **Field names:** checked with a wire-name grep and the vocabulary test before the gate (LESSONS
  2026-10-10). The candidates are `points`, `costs`, `score_min`, `score_max`, `name_max`, `grants`,
  `bonuses`, `choose`, `from`.
- **Tests (`omnis-sim/tests/party.rs` or a new `creation_view.rs`):**
  - The base pack's values: 27, 8..=15, costs `[0,1,2,3,4,5,7,9]`, 6 slots.
  - Agreement:
    - every draft built only from the view is accepted (each race × class × background, the first
      `choose` legal picks, all scores at min)
    - one step past each limit the view reports (score max+1, points budget+1, an extra pick, a
      granted pick) is refused with the matching `CreationError`
  - The op round-trips through JSON. `api_doc` and the vocabulary test pass with the new op.

## P3b. The kit: number controls with slider and arrows, panels in columns
- **`Kind::Number { value: i64, min: i64, max: i64 }`** with a new **`Payload::Set(i64)`**:
  - `apply` accepts Left, Right, Press (steps right) and Set.
  - Set outside min..=max is refused with `Refused::OutOfRange`.
  - Left at min and Right at max change nothing.
- **Renderer:**
  - A number is drawn as its label, then `‹`, a `Slider` with `SliderRange(min..=max)` and `SliderStep(1)`
    and a `SliderThumb` child, then the value, then `›`.
  - The thumb's position is set from `SliderValue` by a small system.
  - Sizes follow `style::scaled`.
- **Router:** an observer on `ValueChange<f32>` from a `Pressable` slider rounds the value
  (`value.round() as i64`, guarded against non-finite values) and queues `Payload::Set`. `applied` takes it
  in the same order as the other inputs.
- **Panels lay out in a row**, each a column. `Screen::shape` counts panels already.
- `screen_text` lists a number as `[number] "STR" 15 (8..15)`.
- `shell/screen.rs` is at 755 lines. Control drawing moves to a new `shell/controls_draw.rs` so both files
  stay under 1000 lines.

## P3c. The CreateParty screen
- **Client state:**
  - `Session.creating: bool`. `new_game` makes the world with an empty party and `creating = true`.
  - `Game` carries `creating`. `nav::base` gives CreateParty when there is a game and (`creating` or no
    members), ahead of Defeat. A loaded save with no members therefore lands in creation, not defeat.
  - `paused()` includes CreateParty, so nothing moves.
  - Pause is not allowed while creating, as under Defeat. Esc on CreateParty does what Back does.
- **`Session::start(config)` (`--seed`, captures, tests) keeps `party::fixed()`**, so the golden replays and
  the direct start are unchanged.
- **Same party on Start again:**
  - `Session.drafts: Vec<Draft>` collects every accepted `Create`.
  - `restart` rebuilds the world from seed and settings and re-applies those drafts through the binder.
  - A loaded save has no drafts, so Start again opens creation with the same seed and settings. Defeat
    keeps its label "Start again".
- **`screen/create_party.rs` (Bevy-free); `CreateForm` lives in `Forms`.**
  - Form fields: name, an index each for race, class, background and alignment, `scores: [u8; 6]` (start
    at min), and picks.
  - The form keeps its state across Back.
  - Heading: "CREATE YOUR PARTY" and "{n} of {slots} members".
  - **Left panel:**
    - Name (Text, `max = name_max`).
    - Race, Class, Background, Alignment (Choice). Labels are race, class and background names from
      `Data`, and alignment words.
    - "Skills (pick N)", then a button per skill on the class list, "[x] Stealth" or "[ ] Stealth":
      - A granted skill is dim, with "from the background" or "from the race".
      - An unpicked skill is dim with "This class picks N skills" when the count is reached.
  - **Right panel:**
    - Six rows: STR … CHA (`Ability::short`) as Number(min..=max), then a dim "+2" when the race gives a
      bonus, then "cost N".
    - "X points spent of Y" (§6.7).
    - "Party", then the members' names from `views.party`.
  - **Footer:** Add member, Begin, Back.
- **Rules the form follows:**
  - A new class clears the picks.
  - A new race or background drops picks it now grants.
- **Add member:**
  - `why_not` comes from `trial::refusal` on the draft, mapped to the old client's words:
    - `PartyFull`: "The party is full"
    - `Name`: "Give the character a name"
    - `Points`: "{spent} points spent of {budget}"
    - `Skills` with the wrong count: "Pick N skills"
    - anything else: the engine's text
  - The first failing check is shown, in the engine's order, which is also the old client's order.
  - Pressed, it gives `Effect::Command { Party(Create(draft)), close: false }`.
  - When the command is accepted, a `Forms::accepted(&Command)` hook, called by `carry_out` on `Ok`, clears
    the form for the next member.
- **Begin:** dim with "Add at least one member" when the party is empty. Otherwise it gives
  `Effect::Host(HostOp::Begin)`, which clears `creating`.
- **Back:** `Effect::ToTitle` then the NewGame form (still filled). This drops the empty or partial world.
- **New ids:**
  - `ScreenId::CreateParty`
  - `ControlId::{Name, Race, Class, Background, Alignment, Score(u8), Skill(u8), AddMember, Begin}`
- **`labels.rs` gains:** `race`, `class`, `background` (text keys from `Data`), `alignment` and `skill`
  (spaced words, "Sleight of Hand"), and `creation_refusal`.
- **`--screen create-party`** is added for captures. It starts a new world with no party.
