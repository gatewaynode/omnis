## Context
A save is bound to the exact packs it was made with. Three things bind it:

1. **The pack fingerprint.** `World.packs` holds each pack's content hash, and `World::from_ron` refuses any
   difference (`LoadError::PackMismatch`) unless forced. The gate is deliberate: it stands guard for the next two.
2. **Definitions saved as numbers.** Content ids (`base:spell:shield`) are interned into `u32` newtypes in file
   order at load, and the world (so the save) stores the numbers. That covers `MapId`, `SpellId`, `ItemId`,
   `MonsterId`, `RaceId`, `ClassId`, `BackgroundId`, `ConditionId`, `FlagId`, `RegionId`, `ServiceId`,
   `ObjectKindId` and `LootTableId`. One new file renumbers every id after it in its kind. M8.5 step 2a item 14
   (`88faba2`) did this to the spells: the v5 and v6 save fixtures had to be renumbered by hand.
3. **References by position into map content.**
   - `MapState.cleared: BTreeSet<u16>` and `EncounterSource::Fixed(u16)` name a fixed encounter by its row in
     the map file.
   - Open doors, ground piles and the automap are stored by cell, and the party's position is a cell.
   - Objects already use string ids (step 2).

PRD §7.7 promises that "a save from build N loads in build N+1". Today any change to a shipped pack breaks that
promise. ARCHITECTURE §4 (progression) and `tasks/knowledge/horizons.md` already list string ids in saves as due
"before much more content arrives". The editor (M5) will change packs all the time, so this comes first.

**Owner's direction (2026-10-15):**
- Option A, a name table carried by the save, chosen over writing names in the world and over pack-assigned
  numbers.
- Placed before the editor.
- Validate on every load request.
- When validation fails, offer migration scripts as an option instead of refusing outright.

**Owner's answers to the plan's questions (2026-10-15):**
1. **Migrations are like database schema migrations:** an ordered chain of scripts, each taking a pack's content
   from one version to the next, applied in order and recorded. The owner asked whether the loose structure
   allows it. It does for content (below); arbitrary transformations would need code, which is a later
   extension.
2. **Nothing is dropped without the player.** No generic fixes: deciding what is trivial would be a judgement
   call. Whatever does not resolve needs a migration, or the load is refused.
3. **No refunds.** Money only matters if the game is ever monetised; it is for casual play at home.
4. **Every pack has a version and a hash in its metadata.** Today `pack.ron` has a version but no hash; the
   loader computes the hash and never records it. Both must always be present in the manifest.
5. **No saving mid-fight.** It avoids more than one sticky problem and is not normal in the genre.

**Found while researching (to be proven red first):**
- `pack.reload` (`ops::check_reload`, both hosts) checks only that the party's tile still exists.
- A reload that adds a content file therefore renumbers ids under the running world without a word: a wizard's
  known spells would silently become other spells.
- The editor's reload and Playtest would hit this constantly.

## Design

### The name table (option A)
- **Where it lives:** the save file gains an envelope:
  `(schema: 8, names: NameTable, world: World)`.
  - `NameTable` holds one list of string ids per id kind; a number's position in its list is what the number
    meant when the save was written.
  - The table is written by `ops::save_text` from `data.registry` (the whole registry, which is deterministic
    and small) and read by `ops::load_text`.
  - It is not a field of `World`, so the in-memory world, `World::fingerprint` and the hot path don't change.
- **Remap on load:** the saved table is compared with the loaded registry by name, building `old number → new
  number` per kind. A pass then rewrites every id field in the world.
  - `Remap` is a trait implemented by every world type that holds an id. It is hand-written, so the compiler
    cannot catch a missed field; the proof test below is the guard.
  - `BTreeMap`/`BTreeSet` keyed by ids (`maps`, `flags`) are rebuilt, because their order changes.
- **When nothing moved,** the remap is the identity: same packs, same world, byte for byte.
- **The proof:**
  - A fixture overlay pack adds one file per kind whose id sorts first, so every number shifts.
  - A world played on the base and test packs is saved, then loaded with the overlay.
  - Every view (`party.get`, `viewport.get`, `combat.get`, `objects.get`, …), all of which name definitions by
    string id, must be equal before and after.
  - A mutation that skips any one id field's remap must fail it.

### Fixed encounters by id
- `FixedEncounter.id` (`[a-z0-9_]{1,32}`, unique in the map, the same rule as object ids) becomes required. The
  test pack's maps gain ids; the base pack has no maps.
- `MapState.cleared` becomes `BTreeSet<String>` and `EncounterSource::Fixed` takes the id.
- The v7 → v8 migration turns rows into ids through the map data the save was made with. A schema-7 save carries
  no name table, so this works only when its pack hashes match, as today (below).

### Validation on every load request
Loading becomes two steps:
1. **`save.check`** reads a save and answers with a `LoadReport`. Nothing changes.
2. **`save.read`** loads, optionally applying the migrations the report offered.

The `LoadReport` holds:
- **Packs:** per pack, saved version and hash, loaded version and hash, and whether they are the same, changed
  or missing.
- **Names:** for each saved name, whether it is found, renamed by a migration, or missing; every missing one is
  listed with where the world uses it (member, kit, map state).
- **Places:**
  - **The position:** the party's tile must exist and be enterable.
  - **Doors:** an open door must still be a door.
  - **Piles:** a pile must lie on ground.
  - **Cleared encounters:** each must still exist.
  - **Automap tiles:** must lie inside the map.
- **The verdict:**
  - `Same`: identical packs. Load as today.
  - `Renamed`: the packs changed, but every name and place resolves. It loads; the client says the packs
    changed.
  - `NeedsMigration`: problems remain, and the packs' migrations resolve them all. The player chooses whether to
    apply them.
  - `Unresolved`: problems remain that no migration resolves. It is refused with the report. Nothing is ever
    dropped to make a save load (owner). `force` has nothing left to do for saves: changed packs that resolve load
    as `Renamed`. The field stays in `save.read` (protocol 2), is ignored, and the changelog says so.

### No saving mid-fight
- `World::may_save` refuses in `Mode::Encounter` and `Mode::Combat`, on every save rule, with its own reason.
- Saves made mid-fight before the rule still load on the packs they were made with (the v5 and v6 fixtures). On
  changed packs they are `Unresolved`, with the reason "saved during a fight", since the remap and validation
  cover the exploring world only.

### Migration scripts (like database schema migrations)
- **The model:** each pack keeps an ordered chain of migrations in `packs/<pack>/migrations/`, one file per
  version step: `0001.ron` takes `0.1.0` to `0.2.0`, `0002.ron` takes `0.2.0` to `0.3.0`, and so on. Loading a
  save made on `0.1.0` under `0.3.0` offers `0001` then `0002`. A step that does not chain (a gap, or two steps
  from one version) is refused at pack load.
- **Recorded:** the save's per-pack fingerprint is updated to the version reached, and the save records the
  migrations applied (`migrated: [(pack, file)]`), as a database keeps its migrations table.
- **Offered, never silent:** the report shows every step and what it would change before the player chooses.
- **Declarative, with no Rhai:** a pack may come from anyone, so migrations stay data checked with limits (§6.2).
  Their steps are the content-level counterparts of a schema change:
  - `Rename { kind, from, to }`: an id renamed or moved between packs (a column renamed).
  - `Replace { kind, from, to }`: a removed definition swapped for another (a spell for a spell, an item for an
    item).
  - `Remove { kind, id }`: a removed definition leaves the world. A removed item leaves the kit and the stores;
    a removed spell leaves the known list and gives back a pick. No refunds (owner).
  - `MovePlace { map, from: (level, x, y), to: (level, x, y) }`: the position, piles and doors on a moved cell.
  - `RenameEncounter { map, from, to }` and `RenameObject { map, from, to }`.
- **Feasibility:** the save is a typed tree, and every way a pack change can break it is one of the three
  couplings above, each with a step that answers it. A change that needs arithmetic (splitting an item into two,
  rescaling a stat on every member) has no step. If one is ever needed, a Rhai `transform` step with a narrow,
  read-and-set API over the save is the extension, with its own plan.
- **Checked at pack load:** every `to` must exist in the loaded packs; the chain must be gapless and end at the
  pack's current version; limits apply (steps per migration, migrations per pack). Each check gets a bad-pack
  row.
- **Drafted by the CLI:** `omnis-cli migration draft --from <old pack dir> --to <new pack dir>` writes the next
  numbered file, listing every removed id and every moved or removed fixed encounter and object as commented
  `Remove` steps, for the author to turn into `Rename`/`Replace` where meant. It cannot guess a rename, so it
  never writes one.
- **`omnis-cli save check <save> --packs …`** prints the report; CI can check the shipped fixtures with it.

### Pack versions and hashes in the manifest
- `pack.ron` gains `hash`, beside `version`. It is the FNV-1a 64 the loader already computes over every data and
  text file in path order, now excluding the manifest's own `hash` field.
- **The loader checks it.** A manifest whose recorded hash differs from the computed one is refused: "content
  changed: raise the version and reseal". A missing hash is refused too.
- **`omnis-cli pack seal <pack> [--version x.y.z]`** records the hash and raises the version (the patch number by
  default). The editor (M5) seals on save. Raising the version is the author's deliberate act, so a changed pack
  never keeps its old version, and a migration always knows which version a save came from.
- `base`, `test` and every fixture pack are sealed in the item that adds this. Tests that change pack files on
  disk reseal them as part of the fixture.

### What stays as it is
- **Replays** still require identical packs (`ReplayError::PackMismatch`): a replay's point is to reproduce.
- **Character snapshots:** hit points, known spells and other figures fixed at creation are not recomputed when a
  pack's balance changes.
- **Schema migrations** (`v1_to_v2` … `v7_to_v8`) stay code, automatic and always applied; pack migrations are
  content, offered.

### `pack.reload`
The running world goes through the same steps:
1. a name table from the old registry;
2. the remap to the fresh one;
3. the same report.

A reload with problems is refused with the report, as today's tile check is.

- `SAVE_SCHEMA` 8, with `v7_to_v8`.
- A `tests/saves/v7.ron` captured by `capture_schema_7_fixture` before the schema moves, while exploring (no
  saving mid-fight).
- Both replays rebaseline once for the schema field.
- Protocol 2, additive: the `save.check` op (MCP `save_check`, tools +1), `save.read` gains
  `migrate: bool` (default false), and `LoadReport` and its verdict are new reply types; vocabulary pins first.

### Client (`omnis-vector`)
- The load screen calls `save.check` first.
  - **`Same` and `Renamed`:** they load; `Renamed` says "Made with older packs; loaded by name."
  - **`NeedsMigration`:** the screen lists the problems and the migration steps, with buttons Apply and load,
    and Cancel (mouse first).
  - **`Unresolved`:** the screen lists what is missing, with Cancel only.
- The save button on the pause overlay is dimmed during an encounter or a fight, showing the reason.
- presentation-ARCHITECTURE and presentation-PRD sections are named when built.

## Decided by me unless the owner objects
- **What counts as a pack's metadata.** The hash goes in each pack's manifest (`pack.ron`), one per pack, not in
  every data file. Per-file hashes would add nothing the pack hash doesn't already catch.
- **No saving in an encounter either**, as well as in a fight: an encounter is the standoff before a fight and
  carries the same stacks.
- **A removed spell still gives back a pick.** That keeps the rules whole and is not a refund.
- **`force` on a save load is ignored** (kept in the protocol, named in the changelog); it never dropped
  anything before either, it only skipped the hash check that names now make unnecessary.
